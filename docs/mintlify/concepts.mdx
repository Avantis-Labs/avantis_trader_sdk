Read this page once. It explains the small set of ideas that every method in both SDKs relies on.

## Human units everywhere

You never deal with on-chain scaling. `100` means 100 USDC, `10` means 10x leverage, and prices are plain decimals such as `3500.5`. The SDK converts to the contract units (1e6 for USDC, 1e10 for prices and leverage) and back. Pass strings when you need exact decimals, for example `collateral="100.25"` in Python or `collateral: "100.25"` in TypeScript.

Two words come up a lot:

- **Collateral** is the USDC you put into a position.
- **Notional** (or position size) is collateral times leverage. Fees and builder fees are computed on notional.

## Two time bases

| Field | Unit |
| --- | --- |
| Intent deadlines | Milliseconds. The SDK sets these for you. |
| Delegate expiry (`expiry_seconds` / `expirySeconds`) | Seconds, as an absolute unix timestamp. |

## Two kinds of keys

- **Your wallet key** can do everything, including approving USDC and moving funds.
- **An API key**, also called a delegate, is a separate key registered to your wallet with one signature. It can trade, but it can never withdraw funds, approve USDC, add other delegates, or act on caller-scoped features such as referrals, claims and the LP vault.

The SDK is in "delegate mode" whenever the signing key's address differs from the trader address you configured. Set `VERANTA_TRADER_ADDRESS` when you use an API key and leave it unset when you sign with the wallet itself. See [Delegates and API keys](/account/delegates).

## Execution routes

By default orders go through the **relayer**, which is gasless: you need no ETH and no RPC. Set execution to `direct` and the SDK signs normal EIP-1559 transactions and broadcasts them through your own RPC instead. The method calls are identical in both modes. [Execution modes](/advanced/execution-modes) has the details.

One exception: full-position take profit and stop loss updates are signed intents that always go to the Veranta operator, even in direct mode, because the contracts have no public entry point for them.

## Pairs

Every method accepts a pair as a symbol or as its index, interchangeably: `"ETH/USD"`, `"eth-usd"`, `"ETH"` or `1`. Upside markets are separate pairs with an `_UPSIDE` suffix, for example `"BTC_UPSIDE"`. See [Markets](/data/markets).

## Receipts and fills

Every write method returns an execution receipt.

| Python | TypeScript | Meaning |
| --- | --- | --- |
| `route` | `route` | `batched-market`, `price-triggers`, `relayer-passthrough`, `twap-api`, `rpc`, or `wallet` (TypeScript browser wallets) |
| `tx_hash` | `txHash` | The on-chain transaction hash once settled. Empty when you pass `wait=False` |
| `request_id` | `requestId` | Relayer queue id, on the relayer passthrough route |
| `tracking_id` | `trackingId` | Batched-market lifecycle id, useful to replay the order's events |
| `order_id` | `orderId` | The on-chain order id, or the TWAP id for TWAP orders |

With the default `wait=True` the call follows the order until it settles or the poll timeout passes. On the batched-market route, which market opens, closes and increases use, the receipt is **fill-aware**: a returned receipt means the order executed, and a declined fill raises `RelayError`. On the other routes the receipt confirms your transaction landed, not that the operator filled the order.

<CodeGroup>

```python Python
receipt = await client.trade.market_open("ETH/USD", "long", collateral=100, leverage=10)
print(receipt.route, receipt.tx_hash, receipt.order_id)
```

```typescript TypeScript
const receipt = await client.trade.marketOpen("ETH/USD", "long", { collateral: 100, leverage: 10 });
console.log(receipt.route, receipt.txHash, receipt.orderId);
```

</CodeGroup>

<Tip>
For position-level confirmation, read `positions()` a moment later, or subscribe to the [order event stream](/data/prices-and-streams#order-events).
</Tip>

## Errors

Every failure is a typed error. Python raises exceptions from `veranta_sdk.errors`; TypeScript throws classes exported from `veranta-sdk`. The names are identical in both, for example `ValidationError` or `RelayTimeoutError`. See [Errors](/advanced/errors).
