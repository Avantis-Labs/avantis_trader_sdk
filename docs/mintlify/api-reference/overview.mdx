These endpoints belong to the Veranta **tx-builder**, a stateless HTTP service that turns every user action on the protocol into a payload you can sign. It holds no keys and stores nothing. You build, you sign locally, you submit.

If you use the Python or TypeScript SDK you never call these endpoints yourself. This reference is for teams building their own stack.

## Base URLs

| Network | Base URL |
| --- | --- |
| Mainnet | `https://tx-builder.veranta.xyz` (this reference renders the mainnet spec) |
| Testnet | `https://tx-builder-testnet.veranta.xyz` |

Every endpoint accepts GET with query parameters and POST with a JSON body. Responses use one envelope: `{ok, data}` on success and `{ok: false, error: {code, message, details}}` on failure.

## The flow

<Steps>
  <Step title="Bootstrap once">
    Call `GET /v2/meta` at startup. It returns the chain id, the contract addresses, both EIP-712 signing domains, enum mappings and unit conventions. Never hard-code any of these.
  </Step>
  <Step title="Build the payload">
    Each action comes in two flavors, matching the two [execution routes](/advanced/execution-modes):

    - **Signable intents** under `/v2/intents/*`, for the gasless relayer route. The response carries the exact EIP-712 typed data (`domain`, `types`, `primaryType`, `message`), its hash, and the ABI-encoded `userIntent`.
    - **Unsigned transactions** under `/v2/trade/*`, `/v2/limit/*`, `/v2/margin/*`, `/v2/position/*` and so on, for self-broadcasting. The response is `{to, from, data, value}`, ready to sign as a regular transaction.
  </Step>
  <Step title="Sign and submit">
    - **Intents.** Recompute the EIP-712 hash locally and check it matches the one in the response, then sign it with the wallet key or a registered delegate key. Signatures are 65 bytes, `r`, `s` and `v` of 27 or 28. Market opens, closes and increases go to the [batched-market endpoint](/api-reference/batched-market), TWAP intents to the TWAP service, and the rest through the relayer. The [direct integrators guide](/migration/direct-integrators) covers the submission targets in detail.
    - **Transactions.** Sign an EIP-1559 transaction and broadcast it through your own RPC, or forward it with `POST /v2/relay`, which only accepts whitelisted contracts and simulates before sending. Check the outcome with `GET /v2/relay/{hash}`.
  </Step>
</Steps>

## Getting a delegate key

You can sign everything with your wallet's own key, but the recommended setup is a **delegate key**, also called an API key: a separate key registered to your wallet that can trade but can never withdraw funds, approve USDC or add other delegates.

- **The easy way:** generate one with the [Veranta API Key Generator](https://delegate.veranta.xyz/). One wallet signature registers it and USDC is approved in the same flow.
- **Programmatically:** generate a key pair, then register it with `/v2/intents/delegate-set` (a gasless `DelegateReq` signed once by the wallet key) or `/v2/delegate/set` (a regular transaction). Check it with `GET /v2/delegation`.

See [Delegates and API keys](/account/delegates) for the permission matrix.

## Conventions that bite people

- **Human units in requests.** `collateralUsdc=100` means 100 USDC and `leverage=10` means 10x. `/v2/meta` documents the on-chain scaling: USDC uses 1e6; prices, leverage and coin exposure use 1e10.
- **Intent deadlines are milliseconds.** Delegate expiry is an absolute unix timestamp in seconds. Do not mix them up.
- **Nonces are an unordered bitmap**, not a counter. Any unused 256-bit value works; `GET /v2/nonce` suggests a free one.
- **A one-time USDC approval** to TradingStorage is required before the first trade, with `/v2/token/approve` or the API Key Generator flow.
