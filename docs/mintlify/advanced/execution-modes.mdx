You choose the execution mode once, with `VERANTA_EXECUTION` or the constructor. Every method call looks the same in both modes.

| | `relayer` (default) | `direct` |
| --- | --- | --- |
| Who pays gas | Veranta. Gasless for you | You. Needs ETH on Base |
| What you need | A signing key | A signing key, an RPC URL and ETH |
| Transport | Signed intents and EIP-7702 smart-account relays | EIP-1559 transactions through your RPC |
| Works with API keys | Yes | Yes, as delegated actions |

<Note>
Some relayer-mode actions ride your EIP-7702 smart account: limit orders, margin changes, approvals, delegate registration and builder-fee orders. They sign an authorization over your account's nonce. An API key is a fresh account, so nothing has to be read from the chain. That is the normal setup. If you sign with your **wallet key** instead, the SDK needs an RPC URL to read that nonce and tells you clearly when it is missing.
</Note>

## Relayer mode

The SDK picks one of four sub-routes per action:

- **Batched market.** Market opens, closes and size increases send a signed intent to the batched-market service. The service prices the order fresh on every attempt, executes it, and streams the lifecycle back: accepted, initiated, then executed or canceled. The receipt route is `batched-market` and it carries a `tracking_id` / `trackingId` for replay and the on-chain `order_id` / `orderId`. A declined fill raises `RelayError`. Sending the intent alone, without the EIP-7702 leg, is the [market-maker fast path](/advanced/mm-fast-path).
- **Price triggers.** Full-position take profit and stop loss updates are signed intents sent to the core API, which executes them through the Veranta operator. Route `price-triggers`. This path is the same in direct mode.
- **Passthrough.** Limit orders, margin, approvals, claims, LP and referral actions are built as transactions and relayed through your EIP-7702 smart account. Route `relayer-passthrough`.
- **TWAP.** TWAP opens, closes and cancels are signed intents sent to the TWAP service, which registers them on-chain itself. Route `twap-api`.

Every signed intent is checked against the hash the API reports before it is signed. See [Security](/advanced/security).

## Direct mode

The SDK fetches the transaction calldata, signs an EIP-1559 transaction and broadcasts it through your RPC. The receipt route is `rpc` and the transaction hash is available immediately.

<CodeGroup>

```python Python
client = AsyncVeranta(execution="direct", rpc_url="https://mainnet.base.org")
```

```typescript TypeScript
const client = new Veranta({ execution: "direct", rpcUrl: "https://mainnet.base.org" });
```

</CodeGroup>

When you trade with an API key in direct mode, calls are wrapped as delegated actions and the API key's address needs ETH for gas.

Two things never go direct: full-position TP/SL updates (no public contract entry point) and builder-fee orders (the fee is charged by the EIP-7702 template, which a plain transaction never runs, so the SDK refuses them rather than silently skipping the fee).

## Browser wallets (TypeScript)

When the signer is a browser wallet from wagmi, the wallet cannot sign EIP-7702 authorizations. Market orders still work through the batched-market route with the intent alone. Passthrough actions fall back to a normal wallet transaction, route `wallet`, and the user pays gas. For popup-free trading, use a [session key](/frontend/react#one-click-trading-with-session-keys).

## Which one should you use?

- **Relayer** for almost everyone: no ETH, no nonce management, and no RPC when you use an API key.
- **Direct** when you must control broadcasting yourself: your own RPC or builder, a custom gas strategy, or no dependency on Veranta infrastructure for submission.

If latency is what you care about, stay on the relayer and use the [market-maker fast path](/advanced/mm-fast-path) to remove HTTP calls from order building.
