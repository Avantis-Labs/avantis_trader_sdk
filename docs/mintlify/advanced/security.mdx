## What an API key can and cannot do

An API key, also called a delegate, signs orders. It never holds or controls funds.

| Action | API key |
| --- | --- |
| Open, close and modify positions | Allowed |
| Set take profit and stop loss, place limit and TWAP orders | Allowed |
| Withdraw or transfer USDC | Impossible. The funds live in your wallet |
| Approve USDC spending | Blocked. Wallet key only |
| Add or remove other delegates | Blocked. Wallet key only |
| Referrals, claims, LP vault, builder code management | Blocked. These are caller-scoped, and the SDK refuses before sending anything |

Delegations expire, and you can revoke one at any time from the [API Key Generator](https://delegate.veranta.xyz/) or with `revoke_delegate` / `revokeDelegate`. Revoking also kills in-flight orders signed by that key. The worst a leaked API key can do is trade on your account until you revoke it.

## Builder fees

When you trade through an app that charges [builder fees](/builders/builder-codes), your USDC allowance goes to the audited BuilderCode registry, never to the app's wallet or to your delegate key. The registry enforces on-chain that a fee is charged only against a real order placed in the same transaction, exactly once, at a rate within the code's public caps, initiated by you or your approved delegate, and paid only to the registered collector.

The one thing to understand: a delegate you approved can charge fees on the orders it places for you, up to the cap times leverage of an order's collateral. Check a code's caps before approving, keep the builder-fee allowance finite, and revoke the delegate to stop everything.

## Signing safety

- **Hash verification.** For every order, the SDK computes the EIP-712 hash locally and checks it against the hash the API sent before signing. A mismatch raises `DigestMismatchError` and nothing is submitted. A compromised or buggy API cannot make the SDK sign something other than what you asked for.
- **Golden vectors.** All 17 order kinds are tested against signature vectors produced by the on-chain hashing library itself, so the local encoding provably matches the contracts.
- **EIP-7702 parity.** The smart-account encoding used by the relayer passthrough is tested byte for byte against the Gelato reference implementation.

## Key handling

- Private keys never leave your process. Only signatures do.
- `register_delegate` / `registerDelegate` uses your wallet key for a single signature and does not store it.
- For production custody, sign with AWS KMS or your own signer so raw key material never touches the host. See [Signers](/advanced/signers).

## A safe setup

1. Generate an API key with the [Veranta API Key Generator](https://delegate.veranta.xyz/). Never put your wallet key on a server.
2. Give the key a finite expiry and rotate it periodically.
3. Call `verify_delegation()` / `verifyDelegation()` when your bot starts, so a revoked or expired key fails fast.
4. Keep only the USDC you want to trade in the wallet the bot operates on.
